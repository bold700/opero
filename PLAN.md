# Opero → Work Order App: Full Implementation Plan

> **Goal:** Turn the current client-only, localStorage, static-export prototype into a
> production MVP matching `work-order-app-spec.md`: real auth (login/2FA/forgot-password),
> Postgres persistence, a proper API backend, and the full sitemap (Dashboard, Work Orders,
> Planning, Customers, Employees, Materials, Reports, Settings) under three roles:
> **Admin / Monteur / Klant**.
>
> **Architecture decision (locked):**
> - Frontend: keep Next.js + React 19 + Tailwind v4 + the existing shadcn/ui components and
>   Zustand store shape. **Leave static export** (`output: "export"` / GitHub Pages) behind.
> - Backend: a **standalone API** (Express on Node, plain and conventional) — NOT a
>   Supabase-client-only app. The
>   frontend never talks to the DB directly.
> - Database: **Postgres** (Supabase-hosted is acceptable as managed Postgres + object
>   storage; we use the Postgres connection + storage bucket, not the Supabase JS SDK in the
>   client).
> - ORM: **Prisma** (the standard Node ORM; great at the deeply-nested reads this domain needs).
> - Auth: own auth in the API (email+password, TOTP 2FA, password reset) issuing JWT access
>   + refresh tokens. No third-party auth dependency.
> - Object storage: Supabase Storage (or S3-compatible) for photos, drawings, signatures, PDFs.
>
> **Roles (locked, per spec):** Admin (full), Monteur (own work orders + limited), Klant
> (view own work orders, manage own profile). The current 7 `AccountRole`s collapse to these 3
> (see Phase 6 for the exact mapping).

## How to use this document

Each **Phase** is written to be executed by an **independent agent** with no shared memory of
the others. Therefore each phase states:

- **Preconditions** — what must already exist (which prior phases).
- **Goal** — one sentence.
- **Files to create / modify** — exact paths.
- **Detailed steps** — numbered, concrete.
- **Data contracts** — types/schemas the phase owns or consumes.
- **Acceptance criteria** — how the agent knows it's done.
- **Verification** — commands to run.
- **Do NOT** — scope guardrails so agents don't collide.

**Repo note (read first, every phase):** `AGENTS.md` warns this is a modified Next.js — APIs
may differ from training data. Before writing Next.js-specific code, read the relevant guide in
`node_modules/next/dist/docs/`. Current versions: Next 16.2.6, React 19.2.4, Tailwind v4,
Zod 4, Zustand 5, Prisma (to be added).

**Current-state facts an agent will rely on:**
- Store: `src/lib/store.ts` — one Zustand store, ~146 keys, `persist` middleware writing a
  single localStorage blob keyed `opero-state-leeg-v1` (version 2, `partialize`d).
- Types: `src/lib/types.ts` — the domain model. Derived logic in `src/lib/stages.ts`,
  `workflow.ts`, `roles.ts`, `pricing.ts`, `catalog.ts`.
- Mock seed: `src/lib/mock-data.ts`.
- Routing: query-param based (e.g. `/project?id=...` via `useSearchParams`), App Router,
  every page is a thin server wrapper around a `*-client.tsx` `"use client"` component.
- Build: `next.config.ts` switches to static export when `BUILD_TARGET=pages`. Deploy is
  `.github/workflows/deploy.yml` → GitHub Pages.

# PHASE 0 — Monorepo restructure & toolchain

**Preconditions:** none. This is first.

**Goal:** Convert the single-app repo into a pnpm workspace monorepo with `client`,
`backend`, and `shared`, without changing any runtime behavior of the web app.

**Files to create / modify:**

  `next.config.ts`, `tsconfig.json`, `postcss.config.mjs`, `eslint.config.mjs`,
  `components.json`, `next-env.d.ts`, `package.json` (the app one), `scripts/`, `demo-recordings/`.

- Create `shared/` skeleton (`package.json`, `tsconfig.json`, `src/index.ts`).

  ```yaml

    - "client"
    - "backend"
    - "shared"
  ```

  `@opero/shared` → `shared/src`.
- Update `.github/workflows/deploy.yml`: builds now run from `client/` (the GitHub Pages export
  build stays working for now — we keep it green until Phase 11 replaces deployment).

**Detailed steps:**

   `pnpm-workspace.yaml`, `.gitignore`, `.git`, `README.md`, `AGENTS.md`, `CLAUDE.md`,

4. Create `shared/package.json` name `@opero/shared`, `"type": "module"`, export `./src/index.ts`.
5. Add `@opero/shared` as a workspace dependency of `@opero/client` (`"@opero/shared": "workspace:*"`).
6. Run `pnpm install` at root; fix path resolution until `pnpm --filter @opero/client build` works

**Acceptance criteria:**
- `pnpm --filter @opero/client dev` runs the app identically to before.
- `pnpm --filter @opero/client build` succeeds; `BUILD_TARGET=pages pnpm --filter @opero/client build` still produces `out/`.

**Verification:**
```

BUILD_TARGET=pages pnpm --filter @opero/client build
```

**Do NOT:** change any component logic, store logic, or domain behavior. This phase is purely

# PHASE 2 — Auth backend (login, JWT, refresh, 2FA, password reset)

**Preconditions:** Phase 1.

**Goal:** Implement the full authentication module per spec (Login, Forgot Password, 2FA) with
JWT access tokens, rotating refresh tokens, TOTP-based 2FA, and password reset.

**Files to create:**
- `backend/src/auth/routes.ts` — Express `Router` mounted at `/api/auth`.
- `backend/src/auth/service.ts` — pure logic (hashing, token mint/verify, totp).
- `backend/src/auth/middleware.ts` — `requireAuth`, `requireRole(...roles)`.
- `backend/src/auth/totp.ts` — TOTP (use `otplib`).
- Deps: `bcryptjs`, `jsonwebtoken`, `otplib`, `qrcode` (for 2FA enrollment QR).

**Endpoints:**
| Method | Path | Body | Returns | Notes |
|---|---|---|---|---|
| POST | `/auth/login` | `{email,password}` | either `{accessToken,refreshToken,user}` or `{mfaRequired:true,mfaToken}` | If `totp_enabled`, return short-lived `mfaToken` instead of tokens. |
| POST | `/auth/login/2fa` | `{mfaToken,code}` | `{accessToken,refreshToken,user}` | Verify TOTP. |
| POST | `/auth/refresh` | `{refreshToken}` | `{accessToken,refreshToken}` | Rotate: revoke old, issue new (`auth_sessions`). |
| POST | `/auth/logout` | `{refreshToken}` | `204` | Revoke session. |
| GET | `/auth/me` | — (Bearer) | `{user}` | Current user. |
| POST | `/auth/forgot-password` | `{email}` | `204` always | Create `password_resets` row, "send" email (log link in dev). Never reveal if email exists. |
| POST | `/auth/reset-password` | `{token,newPassword}` | `204` | Consume reset token. |
| POST | `/auth/2fa/setup` | — (Bearer) | `{secret,otpauthUrl,qrDataUrl}` | Generate + stash pending secret. |
| POST | `/auth/2fa/enable` | `{code}` (Bearer) | `204` | Verify code, set `totp_enabled=true`. |
| POST | `/auth/2fa/disable` | `{password}` (Bearer) | `204` | |

**Detailed steps:**
1. Access token: JWT, 15-min expiry, payload `{sub:userId, role, orgId}`. Refresh token: random
   256-bit, store only SHA-256 hash in `auth_sessions`, 30-day expiry, single-use rotation.
2. Password hashing with bcrypt (cost 12). Generic errors on login failure (no user-enumeration).
3. Rate-limit `/auth/login` and `/auth/forgot-password` (in-memory token bucket per IP for MVP;
   note in code that prod should use Redis).
4. `requireAuth` middleware: parse Bearer, verify JWT, load user, attach `req.user` (extend the
   Express `Request` type via a `declare global` augmentation). `requireRole(...roles)`: 403 if
   `req.user.role` not in list.
5. TOTP via otplib; QR via `qrcode` data URL for the web enrollment screen.
6. Password-reset + login-2fa emails: abstract behind `sendEmail()` that logs to console in dev
   (Phase to wire real provider is out of MVP scope — leave a clear TODO + interface).

**Data contracts (add to `shared/src/schemas.ts`):**
`LoginRequest`, `LoginResponse` (union), `User` DTO (`{id,email,role,name,customerId?,employeeId?,totpEnabled}`),
`RefreshRequest/Response`, `ForgotPasswordRequest`, `ResetPasswordRequest`, `Setup2FAResponse`,
`Enable2FARequest`. Web consumes these in Phase 8.

**Acceptance criteria:**
- Full login→refresh→logout cycle works via curl.
- Enabling 2FA then logging in requires the TOTP code (test with an otplib-generated code).
- Forgot-password creates a reset row and the reset endpoint changes the password.
- Protected route returns 401 without token, 403 with wrong role.

**Verification:** an integration test file `backend/src/auth/auth.test.ts` (vitest) covering
login, 2fa, refresh rotation, reset, role guard. `pnpm --filter @opero/backend test`.

**Do NOT:** build frontend auth UI (Phase 8). Do NOT store raw refresh tokens or reset tokens.

# PHASE 3 — Core domain API (the 146-action surface → REST)

**Preconditions:** Phases 1, 2.

**Goal:** Expose every mutation and query the Zustand store currently performs as authenticated,
role-guarded REST endpoints, grouped by spec module. This is the largest backend phase.

**Strategy:** The store's 146 keys are the spec. Group them into module routers. Each store action
becomes an endpoint; each piece of state becomes a `GET`. Reuse the existing pure domain logic
(`stages.ts`, `workflow.ts`, `pricing.ts`) by moving it to `shared/src/domain/` (Phase 0
created the folder; move the files here and re-export from web).

**Module routers to create under `backend/src/modules/`:**

### 3a. `customers/` (spec: Customers)
- `GET /customers`, `GET /customers/:id`, `POST /customers`, `PATCH /customers/:id`,
  `DELETE /customers/:id` (soft).
- Contact persons: `GET/POST/PATCH/DELETE /customers/:id/contacts`.
- Locations: `GET/POST/PATCH/DELETE /customers/:id/locations`.
- Maps store actions: `addCustomer, updateCustomer, removeCustomer`.
- Guards: Admin full; Klant may `GET`/`PATCH` only **their own** customer (the one their user
  is linked to) — enforce in handler.

### 3b. `employees/` (spec: Employees)
- `GET/POST/PATCH/DELETE /employees`, `POST /employees/:id/roles` (toggle), `GET /employees/:id/timesheet`.
- Maps: `addTeamMember, updateTeamMember, toggleTeamMemberRole, removeTeamMember`.
- Timesheet: aggregate `werkbon_tasks.hours` by employee + date range (spec: Employees→Timesheet,
  and Monteur "view own timesheet").
- Guards: Admin full; Monteur may `GET` own timesheet only; Klant none.

### 3c. `materials/` (spec: Materials)
- `GET/POST/PATCH/DELETE /materials`, `GET/PATCH /materials/:id/inventory`,
  `POST /material-orders`, `GET /material-orders`, `PATCH /material-orders/:id/receive`.
- Maps: `addArticle, updateArticle, removeArticle` (articles/catalog),
  `createPurchaseList, receivePurchaseList`, inventory reads.
- Also `werksoorten`: `GET/POST/PATCH/DELETE /werksoorten` (`addWerksoort, renameWerksoort, removeWerksoort`).
- Guards: Admin full; Monteur may register usage (that lives under work-orders); Klant none.

### 3d. `projects/` (the lifecycle core — largest)
- `GET /projects` (filtered by role visibility — port `getVisibleProjectsForProfile`),
  `GET /projects/:id` (full nested aggregate), `POST /projects`, `PATCH /projects/:id`,
  `DELETE /projects/:id`, `POST /projects/:id/archive`.
- Status/stage: `POST /projects/:id/status` (`moveProjectToStatus`), `POST /projects/:id/stage`
  (`setStage`/`advanceStage`).
- Intake: `PATCH /projects/:id/intake` (`updateIntake`), `POST /projects/:id/intake/complete`
  (`completeIntake`).
- Quote: line items `POST/PATCH/DELETE /projects/:id/quote/lines`, `POST .../quote/from-catalog`
  (`addQuoteLineFromCatalog`), `POST .../quote/send` (`sendQuote`), `.../quote/accept`
  (`acceptQuote`, `acceptQuoteOnly`), `applyNormPrices`.
- Blockers/urgency: `POST /projects/:id/urgency` (`setProjectUrgency`), `.../resolve-blocker`.
- Team: `POST /projects/:id/team` (`setProjectTeam`, `toggleProjectInstaller`).
- Activity/comments: `GET /projects/:id/activity`, `POST /projects/:id/comments`
  (`addProjectComment`). All mutating endpoints append `project_activity` + `audit_log`.
- Meerwerk: `POST/PATCH /projects/:id/meerwerk`, approve office/client, reject, toggle-done.
- Oplevering: `POST /projects/:id/oplevering/init`, toggle items, photos, restpunten, sign.
- Materials check: `POST /projects/:id/materials/check` (`moveToMaterialsCheck`),
  `materialsReady`, `material-requirements` CRUD.
- Guards: Admin full; Monteur read assigned + write only werkbon-scoped things (see 3e);
  Klant read own customer's projects, status/track only.

### 3e. `work-orders/` (spec: Work Orders — the headline module)
Maps the werkbon action cluster. **This is where Monteur "limited" access concentrates.**
- `GET /work-orders` (Admin all / Monteur own / Klant own-customer view-only),
  `GET /work-orders/:id`, `POST /projects/:id/work-orders` (`createWerkbon`/`ensureWerkbon`),
  `PATCH /work-orders/:id`, `DELETE /work-orders/:id`, `POST /work-orders/:id/approve`.
- Drawings: `POST /work-orders/:id/drawings`.
- Tasks (zones): `POST /work-orders/:id/tasks` (`addWerkbonTask`), `PATCH/DELETE .../tasks/:taskId`,
  `POST .../tasks/reorder` (`reorderWerkbonTasks`), `toggleWerkbonTask`.
- Task timing: `POST .../tasks/:taskId/start` (`startTask`), `.../end` (`endTask`), `PATCH .../hours`.
- Task photos: `POST .../tasks/:taskId/photos/before|result`, `DELETE .../photos`.
  **Photo upload = multipart → object storage (Phase 7), store returns storage key.**
- Task materials (the shared line-item row): `POST .../tasks/:taskId/materials` (`addTaakMateriaal`,
  `addTaakRegel`), `PATCH/DELETE .../materials/:matId`, `.../materials/:matId/usage`
  (`setMateriaalUsage`), `.../done` (`toggleMateriaalDone`).
- Completion: `POST /work-orders/:id/complete-all` (`completeAllTaken`),
  `POST /work-orders/:id/finish` (`afrondenWerkbon` — body `{signature}`).
- Signature: `POST /work-orders/:id/signature` → object storage.
- Guards: Monteur may mutate tasks/materials/photos/signature on **work orders for projects they're

# PHASE 5 — Web data layer: replace Zustand-over-localStorage with API client

**Preconditions:** Phases 2, 3, 4.

**Goal:** Swap the web app's persistence from localStorage to the API, **without rewriting the
~13k LOC of components**, by keeping the Zustand store's public shape and changing its internals to
call the API.

**Approach (chosen for least churn):** Introduce TanStack Query for server state, and convert the
Zustand store actions into thin wrappers that call a typed API client + invalidate queries. Reads
move to query hooks; the store keeps holding session/UI state (`activeProfileId` → real auth user,
`projectsViewByProfile`, dialogs).

**Files:**
- `client/src/lib/api/client.ts` — typed fetch wrapper: base URL from env, attaches access token,
  auto-refreshes on 401 (calls `/auth/refresh`), throws typed errors.
- `client/src/lib/api/*.ts` — one module per backend module (customers, projects, work-orders,
  planning, materials, employees, dashboard, invoices, auth). Each exports typed functions +
  TanStack Query hooks (`useProjects`, `useProject`, `useCreateWerkbon`, ...).
- `client/src/lib/store.ts` — **refactor**: remove `persist`/`localStorage` and mock seeding.
  Keep UI/session slices. Re-implement each mutating action as `async` calling the API client +
  invalidating the right query keys (or delete the action and move callers to mutation hooks —
  decide per action; prefer hooks for new code, keep store wrappers where many components call it).
- `client/src/app/providers.tsx` — wrap app in `QueryClientProvider` + auth context.
- Add `@tanstack/react-query`.

**Detailed steps:**
1. Build the API client with token storage in memory + httpOnly-cookie refresh (or localStorage
   refresh token for MVP — document the tradeoff; prefer cookie).
2. For each spec module, implement read hooks first (replace store-state reads in the matching
   `*-client.tsx`). Then mutation hooks.
3. Replace `useOperoStore((s)=>s.projects)` etc. with `useProjects()` query, page by page. Keep the
   store action names alive as deprecated wrappers during transition so unconverted components
   don't break; remove them once their callers are migrated.
4. `activeProfileId` / profile-switcher (`DevSettingsSheet`) → replaced by real auth: the "current
   user" comes from `/auth/me`. The dev profile-switcher becomes (a) gone in prod, or (b) an
   admin-only "impersonate" behind a flag. For MVP: remove fake switching, wire to real login.
5. `resetDemo` → remove (was localStorage-only).

**Migration order (so the app stays runnable):** customers → employees → materials/werksoorten →
articles → projects list → project detail → work orders → planning → dashboard → invoices.

**Acceptance criteria:**
- App runs with the API as the only data source; killing localStorage has no effect on data.
- Every previously-working interaction (create project, edit werkbon, drag planning, sign-off,
  invoice) works against the API.
- No remaining import of `mock-data.ts` in runtime web code (only seed uses it, in the API).

**Verification:** manual click-through of the happy path against a seeded API; the Playwright
happy-path script (`scripts/record-happy-path.mjs`) updated to run against the API-backed app and
passing.

**Do NOT:** change visual design or component structure beyond data wiring. Keep the existing UI.
